# Reviewed Release Manifests

Publication requires `release-manifests/<package-version>.json`. The workflow
compares the single packed tarball with this reviewed file before publishing.
Missing approval, extra/missing files, changed sizes or changed SHA-256 hashes
stop the workflow. No approval manifest is generated by CI or supplied by this
gate's implementation.

The JSON schema is exactly:

```json
{
  "commit": "reviewed source commit",
  "archive": "tarball basename (not a local username or absolute path)",
  "integrity": "sha512 SRI of the reviewed local tarball",
  "files": [
    { "path": "package.json", "size": 123, "sha256": "64 lowercase hex digits" }
  ]
}
```

List every regular file relative to `package/`. Entry order does not matter.
Paths are ASCII, relative, unique even under case folding, and cannot contain
dot segments. Names/sizes/hashes are compared against the actual archived bytes.
The packed package name and version must also match the checkout.

Serialize approval JSON as `JSON.stringify(manifest, null, 2) + "\n"`, with
UTF-8 and LF. Other representations, including duplicate JSON keys, are rejected
instead of allowing a last-key-wins interpretation to mislead the reviewer.

The first three fields are audit metadata, not equality checks: adding the
reviewed manifest changes HEAD, and rebuilding may change compression without
changing content. The verifier reports the actual tarball SRI on success.

Build the final candidate outside publication CI, record its file manifest,
obtain independent review, then commit only the approved manifest. Manifests
and scripts are excluded from package contents, avoiding self-hashing. The
reviewed git ref and npm environment are the trust boundary, not a separate
cryptographic approval signature. Editing this workflow does not approve a
candidate, push, tag, or publication.

Code and build dependencies running earlier in the job are trusted. This gate
detects content drift; it does not isolate publication from a hostile toolchain.
Independent human approval relies on repository review and environment protection
rules, which must be verified separately. File modes, ownership and timestamps
are not part of the content manifest; entry types must still be regular files.

The read-only verifier accepts regular ustar files with plain octal headers;
links, directories, devices, PAX/GNU extensions and malformed/truncated archives
fail closed. Input sizes and decompression are bounded. Build approval using
the same npm major and LF checkout as CI: differing file bytes are never
silently normalized. Unknown CLI arguments fail; there is no write/update mode.
